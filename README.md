# StockMarketSimulator

Система сбора, обработки и хранения рыночных данных в реальном времени: три имитатора бирж (WebSocket-серверы с разными форматами и управляемыми сбоями) и сервис-агрегатор, который собирает потоки, нормализует, дедуплицирует и пишет в PostgreSQL.

## Быстрый старт

```bash
echo "POSTGRES_PASSWORD=postgres" > .env   # compose читает пароль отсюда
docker compose up --build
```

| Сервис | Адрес |
|---|---|
| exchange-alpha / beta / gamma | `http://localhost:5001..5003/swagger` (chaos-эндпоинты) |
| aggregator | `http://localhost:5100/metrics` (Prometheus), `/health` |
| Grafana | `http://localhost:3000`, дашборд «StockMarket: pipeline health» (anonymous admin) |
| Prometheus | `http://localhost:9090` |

Без Docker (тесты и локальная разработка), из папки `StockMarket`:

```bash
cd StockMarket
dotnet test                                                   # 39 тестов, включая проблемные сценарии
dotnet run --project StockMarketImitator --launch-profile exchange-alpha   # или exchange-beta / exchange-gamma
dotnet run --project StockAggregator                          # порт 5100
```

## Архитектура

```
 alpha ──┐
 beta ───┼── WS ──► connector ×3 ──► [bounded channel] ──► processing ──► [bounded channel] ──► batch writer ──► PostgreSQL
 gamma ──┘        per-source,        raw, 20k               normalize,    normalized, 20k        COPY 500/200ms      temp + ON CONFLICT
                  reconnect+idle                               dedup 60s
```

Каждый источник это отдельный `ExchangeConnectorWorker`: проблема одного не влияет на остальных. Между стадиями стоят ограниченные каналы (`System.Threading.Channels`), поэтому давление медленного потребителя передаётся до самых сокетов (backpressure), а суммарная память конвейера имеет известный потолок.

## Имитаторы бирж

| Биржа | Пример сообщения | Особенности |
|---|---|---|
| Alpha | `{"symbol":"AAPL","price":187.3,"qty":100,"ts":"2026-01-05T12:30:00Z","seq":1042}` | JSON, время ISO-8601 |
| Beta | `{"s":"AAPL","p":"187.30","v":100,"t":1754302530123,"n":1042}` | цена строкой (invariant), время unix-ms |
| Gamma | `["AAPL",187.3,100,1754302530,1042]` | позиционный массив, unix-секунды |

Chaos-эндпоинты (Swagger на каждом порту): `POST /chaos/disconnect` рвёт соединения; `POST /chaos/duplicates?rate=0.5` задаёт долю ретрансляций; `POST /config/rate?ticksPerSecond=N` меняет нагрузку на лету. Пустое соединение держится application-level heartbeat'ом (`{"type":"heartbeat"}`), потому что в `System.Net.WebSockets` нет API для protocol ping.

## Решения

**Дедупликация.** Ключ: `(SourceId, SourceSeq)`. Биржа ретранслирует тик с тем же seq, поэтому пара «источник + биржевой id» однозначна. Окно 60 секунд, скользящее (eviction каждые 10 с): покрывает ретрансляции при переподключении и типовые задержки, память ограничена. Потокобезопасность даёт `ConcurrentDictionary.TryAdd` как единая атомарная операция check-and-add, без локов. Второй уровень защиты: PK `(source, seq)` в PostgreSQL, то, что память пропустила (например, после рестарта агрегатора), отсечёт БД. Если у биржи нет собственного seq, fallback это контентный ключ (хеш полей тика); у всех трёх форматов seq есть, поэтому в коде не реализовано, осознанное упрощение.

**Запись в БД.** Батчи по 500 тиков или 200 мс (что раньше; окно стартует с первого элемента батча и не продлевается). Вставка: `COPY` в temp-таблицу + `INSERT ... SELECT ... ON CONFLICT DO NOTHING` в одной транзакции. У `COPY` нет conflict handling, а поштучный INSERT на потоке в тысячи тиков/с это лишние round-trip'ы. ORM здесь не нужен: схема из одной таблицы, запросы сырые и предсказуемые.

```sql
CREATE TABLE ticks(
    source  text        not null,
    seq     bigint      not null,
    ticker  text        not null,
    ts      timestamptz not null,
    price   numeric     not null,
    volume  numeric     not null,
    primary key (source, seq));

CREATE INDEX ix_ticks_ticker_ts ON ticks(ticker, ts);
```

**Ошибка БД.** Ретраятся только transient-ошибки (`NpgsqlException.IsTransient`, таймауты, сокеты), 5 попыток с экспоненциальной паузой; постоянную ошибку ретраить бессмысленно. Если попытки исчерпаны, батч отбрасывается, но **каждый потерянный тик считается** (`aggregator_ticks_dropped_total`) и логируется ошибкой: потерь молча нет, это решение, а не проглоченное исключение.

**Переподключение.** Экспоненциальный backoff с full jitter `random(0, min(30s, 1s·2ⁿ))`, без лимита попыток. Джиттер разносит реконнекты нескольких источников, чтобы они не долбили перезапущенный сервер одновременно. «Зависшее» соединение (полуоткрытый TCP сам о себе не сообщает) детектится idle-таймаутом 15 с: тишина на проводе = мёртвое соединение, идём в тот же reconnect-путь. Даже вежливое закрытие сервером переподключается не мгновенно: минимальная пауза 1 с против tight-loop.

**Graceful shutdown.** Остановку распространяет не раздача `CancellationToken`, а цепочка completion каналов: коннекторы (единственные, кто слушает токен) -> `Complete` raw-канала -> processing дочитывает и закрывает normalized -> батчер сливает остаток в БД. Иначе нижние стадии умирают раньше верхних и теряют хвост. Порядок регистрации hosted-сервисов = порядок остановки (хост стопает в LIFO), коннекторы зарегистрированы последними, останавливаются первыми. Общий бюджет: `ShutdownTimeout` 30 с.

**Расширяемость.** Новая биржа = новый `INormalizer` (один класс) + строка в конфиге. Существующий код не меняется.

## Проверка на стенде

Прогон на 2 vCPU, PostgreSQL 17.10, .NET 10. Суммарный поток ~1400 тик/с (имитаторы выдают ~465 т/с при лимите 350: `Task.Delay` на Linux точнее квоты, получается «не меньше заданного»).

| Сценарий | Результат |
|---|---|
| Нагрузка ~1400 т/с, 10+ мин | 83k тик/мин записано, **dropped = 0**, дыр в seq нет; RSS со 166 до 174 МБ (плато GC), feed-lag p50 < 1 мс (p95 деградирует на 2 перегруженных ядрах, артефакт стенда) |
| Обрыв источника (`/chaos/disconnect`) | backoff 0.7 с, переподключён; скорость записи остальных источников не изменилась (~1350 т/с) |
| Дубли 50% на beta, 60 с | получено 27 430, отфильтровано **13 707 (50.0%)**, уникальные записаны все |
| БД мертва 45 с | каналы заполнились ровно до ёмкости (20 000/20 000) и остановились, RSS +1 МБ; 3 батча (1500 тиков) отброшены после ретраев (**посчитаны и залогированы**); после поднятия БД каналы осушились за секунды |
| SIGTERM под нагрузкой | полная остановка за ~250 мс; 301 тик «в полёте» долетел в БД; счётчик written == строкам в БД точно |

Что тестирование реально поймало (исправлено до сдачи): стойло остановки из-за порядка регистрации hosted-сервисов; гонка drain'а в тестах из-за того, что в .NET 9+ `BackgroundService` запускает `ExecuteAsync` через `Task.Run` с токеном остановки; двойное перечисление ленивого `IEnumerable<IHostedService>` в DI, из-за которого `StopAsync` видел новые, никогда не запущенные воркеры, а настоящие продолжали писать.

## Тесты (39)

- **Имитатор (9):** контракты форматтеров, монотонность seq, границы random-walk, chaos-состояние.
- **Нормализация и дедуп:** контракты трёх форматов (включая цену-строку под `ru-RU` локалью), битые входы без исключений, фаззинг 1000 случайных строк; дедуп под конкуренцией: 100k тиков с 50% дублей, перемешанных по потокам, проходят ровно уникальные.
- **Проблемные сценарии:** переподключение после обрыва многократно и без влияния на стабильный источник (реальные сокеты против scripted-сервера на Kestrel); молчащее соединение убивается idle-таймаутом; фрагментированное WS-сообщение собирается из 3 фреймов; drain батчера; постоянная ошибка БД считается; end-to-end хаос (дубли + обрывы каждые 100 тиков), каждый seq ровно один раз; регрессии на найденные баги остановки.

## Мониторинг

Prometheus-метрики на `/metrics`: скорость по источникам, нормализовано/дедуплицировано/записано/отброшено, reconnects и `source_up` по источникам, заполненность обоих каналов (индикатор backpressure), размер окна дедупа, гистограмма feed-lag. Лейблы только source (3 значения): тикер в лейблах взорвал бы кардинальность. Готовый дашборд Grafana лежит в `observability/`.

## Известные ограничения

- Дедупликация только в памяти. После рестарта агрегатора окно теряется; защиту от старых seq даёт только первичный ключ `(source, seq)` в PostgreSQL.
- При обнулении seq на стороне биржи новые тики в течение окна (60 с) будут отфильтрованы как дубли. Нужен session-id в ключе — не реализовано.
- Один инстанс. Горизонтальное масштабирование требует шардирования источников и внешней дедупликации.
- При permanent-ошибке БД после 5 ретраев батч отбрасывается (считается и логируется). Dead-letter нет.
- `/health` — только liveness, не учитывает готовность БД и состояние источников.
- Heartbeat определяется по подстроке `"heartbeat"`. При текущем наборе тикеров риск ложного срабатывания минимален; типизированный протокол не вводился.
- Feed-lag gamma завышен из-за секундного разрешения времени на бирже. В распределённой среде требуется синхронизация часов.
- Миграции это один SQL-скрипт. Для роста схемы понадобится полноценный мигратор.
